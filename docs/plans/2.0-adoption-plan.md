# AI Context Kit: adoption plan (skills, OpenSpec, installer)

Sep 27, 2026 · @Marco S.

The kit should keep owning *who and how* (user context, AGENTS.md, session state, validation), hand *what gets built* to OpenSpec, borrow the strongest disciplines from mattpocock/skills, and ship a Node-based per-repo installer that also sets up OpenSpec, since OpenSpec already makes Node a prerequisite. No code was changed; this is a plan.

## Part 1: What to take from mattpocock/skills

Fifteen items are worth adopting outright and thirteen more in adapted form; the rest either duplicate OpenSpec or are tied to one harness. The strongest ideas are method, not files: the relentless interview Matt calls grilling, a ubiquitous-language glossary, the user- vs model-invoked split, and the two-axis review.

Verdicts: **Adopt** (take as is, reworded to kit conventions), **Adapt** (take the core, change the shape), **Later** (worth it after Parts 2 and 3), **Skip**.

## Side findings in the kit

Comparing the repos surfaced six small drifts in the kit (commit `50c264c`); fixing them first makes Parts 2 and 3 cleaner.

- **Invocation claim without a file.** README says `repository-drift-control` needs explicit invocation (`allow_implicit_invocation: false`), but the `agents/openai.yaml` sidecars were deleted in 1.4.2, so Codex can fire it implicitly.
- **Path mismatch in the loop.** `01-readiness-check` and `02-implementation` read `docs/adrs/`, while arc42 §9 is the ADR home in the arc42 toolkit; the same prompts read `specs/` then `docs/specs/`, which OpenSpec replaces with `openspec/specs/` and `openspec/changes/`.
- **Manual placeholders.** `04-learnings` stops until `[PRIMARY_STACK]` and four other placeholders are hand-edited in the prompt file; the user context already holds stack and background, and an installer could fill the rest.
- **Repeated "How to Invoke" block.** Every `SKILL.md` carries paste/upload instructions that cost context on every run inside a harness; they belong in the per-skill docs page.
- **Generic skill names.** `create-skill`, `validate-skill` and similar are namespaced only when installed as a plugin; copied into `.agents/skills/` they can collide with other skill sets.
- **Windows symlinks.** `.agents/skills/` relies on symlinks that break on Windows without Developer Mode; a copying installer removes the caveat.
- **Two creators, one file.** `create-agents-md` writes the entry-point half of `AGENTS.md` and `create-project-instructions` the project-context half, each with its own validator, while the template and the kit's own `AGENTS.md` combine both; they overlap on session state and the command namespace (merged in 2.0, see Decisions).

## Part 2: Making OpenSpec mandatory

OpenSpec becomes the only door through which a behaviour change enters a kit-managed repo: no apply-ready change, no implementation. The kit wraps OpenSpec and customises it only through `openspec/config.yaml`; it never edits OpenSpec's generated skills, because `openspec update` overwrites them and OpenSpec's own docs list editing them as an unsolved gap.

### Who owns what

| Concern | Owner | Artifact |
| --- | --- | --- |
| Who the user is, how to collaborate | Kit | User context, `AGENTS.md` session state |
| What the system must do | OpenSpec | `openspec/specs/` |
| What is changing now, and why | OpenSpec | `openspec/changes/<id>/` (proposal, specs deltas, design, tasks) |
| Why the architecture has this shape | arc42 toolkit | `docs/arc42/` (master), ADRs in `docs/adr/` indexed by §9 |
| How work is executed and gated | Kit loop | `prompts/loop/`, self-review `STATUS` |
| Planning context OpenSpec injects | Kit (generated) | `openspec/config.yaml` `context`, `rules`, `operations` |

### What "mandatory" means

Proposed as a new normative section in the session spec (kit 2.0.0, since it is breaking):

- A kit-managed repo **MUST** contain an initialised `openspec/` and at least one OpenSpec tool integration.
- The Implementation phase **MUST** start only against an OpenSpec change that `openspec status --change <id> --json` reports as apply-ready.
- Changes with no behaviour impact still get a change folder with `skip_specs: true`, OpenSpec's own escape hatch, so there is one path for all work.
- Generated `openspec-*` skills and commands **MUST NOT** be edited; customisation goes through `openspec/config.yaml` or, later, a forked schema.
- Chat-only surfaces (Claude Projects, ChatGPT, Le Chat) cannot run the CLI: OpenSpec skills are restricted to `Bash(openspec:*)`. There the kit runs in a fully supported **manual mode**: planning (proposal, spec deltas, design, tasks) happens anywhere, from templates generated out of OpenSpec's shipped schema at each kit release; validate, apply and archive happen in a repo with the CLI.
- The spec sets a minimum OpenSpec version (1.13.2 today; newer versions warn, never fail), reviewed every three months and checked by `ai-context-kit doctor` (Part 3).
- OpenSpec sends anonymous usage stats by default; kit docs name the opt-out (`openspec config set telemetry.enabled false`, or `OPENSPEC_TELEMETRY=0`) and the installer asks.

The accented gate is the new rule: `01-readiness-check` stops unless the target change is apply-ready. The self-review's Spec axis now has a real contract to check against, instead of prose specs.

### Customising OpenSpec from the kit

`openspec/config.yaml` is the only lever, and each field reaches a known step:

- **`context`** (every artifact, apply, archive): short pointer lines, not copies. For example: follow `AGENTS.md`; use the glossary (arc42 §12 when arc42 exists, otherwise `CONTEXT.md`); respect ADRs in `docs/adr/`; plus the two or three facts that shape every plan (target platforms, architecture style).
- **`rules.proposal`**: run `ack-interview-with-context` first when the change touches domain language.
- **`rules.design`**: name the test seams and confirm them with the user; flag any ADR the design contradicts.
- **`rules.tasks`**: tracer-bullet vertical slices, each demoable; blockers listed per task group; expand-contract for wide refactors.
- **`operations.apply`**: use the `tdd` skill at the agreed seams; run build and tests before ticking a task.
- **`operations.archive`**: list arc42 sections that need updating and run the matching arc42 skill; promote `design.md` decisions that pass the ADR test to `docs/adr/`; archive as the last commit on the feature branch.

A forked schema (for example `ack-spec-driven` with an `adr` artifact) stays out of scope for now: OpenSpec marks schema commands as experimental, and config rules cover the need.

## Part 3: A per-repo, tool-independent installer

Build `@msiccdev/ai-context-kit`, a small Node CLI on npm with the bin `ai-context-kit`, fronted by an agent-executable `install.md`: every kit repo already needs Node 20.19 or later for OpenSpec, so Node adds no new prerequisite. The CLI does the deterministic work (detect, copy, record, run `openspec init`); the `ack-setup` skill does the judgement work (explore the repo, interview briefly, write `AGENTS.md` content), following the setup pattern from Part 1. Docs always show the scoped name, because unscoped `ai-context-kit` on npm is an unrelated tool.

### Requirements

- Per repo and committed with the code, so teammates get the same install.
- One run serves several tools: Claude Code, Codex, GitHub Copilot, Cursor, Gemini CLI, Mistral Vibe and the shared `.agents/skills/` target.
- Idempotent `init`; an `update` that never overwrites a user's edits.
- Sets up OpenSpec in the same run, with consent before any global install.
- macOS, Linux and Windows, without symlinks.
- Non-interactive flags for CI and for agents.
- Coexists with OpenSpec and other skill sets in shared folders.

### Options compared

| Option | For | Against | Verdict |
| --- | --- | --- | --- |
| A. Node CLI on npm (`npx <pkg> init`) | One codebase for every OS; same runtime OpenSpec needs; can call `openspec init`; testable; version pinned per run | Build, tests and npm publishing to maintain | Recommended engine |
| B. `install.sh` + `install.ps1` | No runtime | Two implementations drifting apart; weak YAML and JSON merging; hard to test | No |
| C. skills.sh only (`npx skills add MSiccDev/ai-context-kit`) | Zero build; many agents supported | Copies skills only: no `AGENTS.md`, no OpenSpec, no manifest, no safe update | Extra channel |
| D. Agent-driven `install.md` only | Adapts to any tool; no code | Results vary by model | Front door that runs A |
| E. Existing plugins | Global and auto-updating | Per user, not per repo; three ecosystems only | Keep for personal use |

### Command surface

| Command | What it does |
| --- | --- |
| `npx @msiccdev/ai-context-kit@latest init [path] --tools <ids\|all\|none> --profile <core\|full> --yes --dry-run` | Detects tools (or takes `--tools`), copies skills, writes instruction bridges and marker blocks, writes the manifest, runs the OpenSpec steps below |
| `ai-context-kit update [--force]` | Refreshes managed files whose hash still matches the manifest; then offers `openspec update` |
| `ai-context-kit doctor [--json]` | Checks Node and OpenSpec versions, `openspec/` root, manifest integrity, locally edited files, duplicate skills from a plugin install, the `AGENTS.md` OpenSpec section |
| `ai-context-kit tools` | Lists tool ids, skill paths and invocation spelling |
| `ai-context-kit remove` | Deletes only files the manifest owns |

Without a global install, every command runs as `npx @msiccdev/ai-context-kit <command>`. The closing message of `init` names the `ack-` skill prefix and the first skill to run, `ack-setup`.

### File ownership and safe updates

- **Manifest** at `.ai-context-kit/manifest.json`: kit version, repo profile, tools, and for each written file its path and the sha256 of what was generated.
- **Update rule**: hash unchanged, overwrite; hash changed (the user edited it), write `<file>.ai-context-kit-new` beside it and report; file deleted on purpose, leave it deleted. This closes the gap OpenSpec still has, where `update` overwrites edited skills.
- **Marker blocks** `<!-- AI-CONTEXT-KIT:START -->` and `<!-- AI-CONTEXT-KIT:END -->` for kit-owned sections inside `AGENTS.md` and `CLAUDE.md`; text outside them is never touched (the pattern OpenSpec used with `<!-- OPENSPEC:START -->`).
- **Provenance**: each installed `SKILL.md` carries `generatedBy: ai-context-kit@<version>` in `metadata`, as OpenSpec does, so `doctor` can spot stale copies.
- **Shared folders**: the installer touches only `ack-*` folders listed in its manifest, never `openspec-*` or `.openspec-target`.
- **Profile per repo**, stored in the manifest; OpenSpec's profile is machine-global, which lets teammates drift apart.
- **Bundled content**: skills ship inside the npm package, so an install never fetches from GitHub and is reproducible.
- **Codex sidecars** (`agents/openai.yaml`) are generated from each skill's new `invocation` field.
- **User context** stays personal and outside the repo; `ack-setup` asks where it lives and how each tool loads it, and never copies it in.

### OpenSpec steps inside `init`

1. Check `node --version` is 20.19 or later; otherwise stop with guidance, never switch versions for the user.
2. Check `openspec --version` against the kit's minimum; if missing or older, show the install command and wait for consent. No sudo, no edits to shell profiles: the same rules OpenSpec's own `install.md` sets for agents.
3. Ask about the telemetry opt-out and apply the answer.
4. Run `openspec init --tools <same ids>` and relay what it printed.
5. Seed `openspec/config.yaml` with the kit's `context`, `rules` and `operations` when those keys are absent; when present, show a diff and ask. YAML has no HTML comments, so kit-owned keys get a `# ai-context-kit:managed` comment instead of marker blocks.
6. Verify with `openspec list --json` (a non-null `root`) and record the OpenSpec version in the manifest.

### Front door: `install.md`

An agent-executable file at the repo root, modelled on OpenSpec's: OBJECTIVE, DONE WHEN, TODO, then steps that check Node, confirm the folder, infer the tools the agent is running in, run `npx @msiccdev/ai-context-kit@latest init --tools <ids>`, invoke `ack-setup`, and report the exact invocation spelling per tool. The README install block points to it ("paste this into your agent") beside the plain CLI command.

### Testing

- Fixture repos per tool, with golden-file snapshots of what `init` writes.
- A parity test that installed skill bodies equal the `skills/` sources, like OpenSpec's skills.sh parity test.
- Update-safety tests: edited file produces `.ack-new`, deleted file stays deleted.
- End-to-end run of real `openspec init` in a temp repo.
- CI matrix: Windows, macOS, Linux.

### Rollout

1. **Spike and ADR.** Verify instruction-file support per tool; register the `@msiccdev` npm scope.
2. **MVP.** `init`, `update`, `doctor` for `claude`, `codex`, `github-copilot`, `agents`; manifest; marker blocks.
3. **OpenSpec orchestration.** Steps 1 to 6 above, including config seeding.
4. **Agentic half.** `ack-setup` skill and `install.md`.
5. **Breadth.** `cursor`, `gemini`, `vibe`; `remove`; `--dry-run`.
6. **Release.** Publish to npm, rewrite the canonical install block, retire the template-repository path the README already marks as phasing out.

How credit is recorded:

1. **Skill metadata.** Each adapted skill carries one string, keeping the kit's rule that `metadata` values are strings: `credits: "Adapted from mattpocock/skills grilling (MIT, Copyright (c) 2026 Matt Pocock), https://github.com/mattpocock/skills"`.
2. **Skill body.** A renamed concept names its origin once, for example "`ack-interview` adapts Matt Pocock's grilling skill".
3. **Near-verbatim passages** (such as the smell baseline list or the ADR test) get a `CREDITS.md` in the skill folder, the pattern Matt uses for his own `pr` skill.
4. **Central notice.** `THIRD_PARTY_NOTICES.md` at the repo root holds both full MIT texts and a list of adapted skills; the npm package ships it, and the installer copies it next to installed skills.
5. **README.** An Acknowledgments section names both projects and what came from each.
6. **Validation.** `ack-validate-skill` flags a skill that adapts external material without a `credits` entry, and `ack-drift-control` checks `THIRD_PARTY_NOTICES.md` stays in step with the skills that declare credits.
